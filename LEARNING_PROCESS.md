Последнее обновление: 2026-08-13

## Как мы работаем

Пользователь пишет код вручную. Codex помогает как наставник:

1. Мы выбираем одну задачу.
2. Codex объясняет проблему, ожидаемое поведение и критерии готовности.
3. Пользователь вносит изменения.
4. Codex проводит review через Git diff и указывает конкретные места для исправления.
5. После успешных `lint`, `build` и ручной проверки Codex предлагает состав и сообщение атомарного коммита.
6. Коммит или push выполняется только после явного подтверждения пользователя.
7. Одновременно держим только одну активную feature-ветку. После merge в `dev` и push завершённую feature-ветку удаляем локально и на GitHub.

Статусы: `[ ]` не начато, `[~]` в работе, `[x]` завершено, `[!]` заблокировано.

## План полного MVP и контрольная точка к 12 августа 2026

### Принятое ограничение времени

- Пользователь пишет код максимум 2 часа в день.
- С 7 по 12 августа включительно доступно 12 часов.
- Полный объём ниже оценивается в 47–59 часов чистой реализации и не помещается в 12 часов.
- Контрольная точка 12 августа: завершённая страница товара, базовая аутентификация email/password и демонстрационный checkout без реальной оплаты.
- Google OAuth, Stripe, реальные заказы, история заказов и admin CRUD перенесены на развитие проекта после дедлайна.

### Сокращённый demo-MVP к 12 августа

- Auth: регистрация и вход по email/password, выход и сохранение сессии после refresh.
- Username: временно хранится в Supabase user metadata; отдельный уникальный `profiles.username` переносится на следующий этап.
- Checkout: контактные данные, адрес доставки, сводка корзины и клиентская валидация.
- Demo payment: кнопка подтверждает тестовый заказ, очищает корзину и открывает success-страницу; данные банковской карты не запрашиваются.
- Перед сдачей: `git diff --check`, `npm run lint`, `npm run build` и ручной smoke test полного demo-сценария.

### Цель полного MVP

Полный MVP считается завершённым, когда работает один сквозной сценарий:

1. Пользователь создаёт аккаунт по email и паролю либо входит через Google OAuth 2.0.
2. Пользователь открывает полноценную страницу товара и добавляет доступный товар в корзину.
3. Checkout создаёт заказ и переводит пользователя на Stripe-hosted Checkout в test mode.
4. Подписанный Stripe webhook подтверждает оплату и меняет статус заказа.
5. Пользователь видит оплаченный заказ и его позиции в своей истории.
6. Администратор через защищённую панель добавляет и редактирует товары, задаёт скидку, отмечает товар недоступным и архивирует его.

### Зафиксированный объём полного MVP после дедлайна

- Страница товара: данные из Supabase, loading/error/not-found/success, цена со скидкой, доступность, корзина и избранное.
- Auth: регистрация и вход по email/password, выход, сохранение сессии, Google OAuth, профиль с уникальным `username`.
- Checkout: контактные данные и адрес доставки, сводка корзины, серверный пересчёт цен, Stripe Checkout test mode, success/cancel страницы.
- Заказы: таблицы `orders` и `order_items`, статусы как минимум `pending`, `paid`, `failed`, `cancelled`, снимок названия и цены товара на момент покупки.
- История заказов: только собственные заказы текущего пользователя, защищённые RLS.
- Админка товаров: список, создание, редактирование, `discount_price`, `is_available`, архивирование через `is_active=false`.
- Безопасность: роль администратора хранится в Supabase и проверяется RLS; Stripe secret key и webhook secret доступны только Edge Functions.
- Проверка: `git diff --check`, `npm run lint`, `npm run build` и ручной end-to-end сценарий.

В полный MVP не входят: числовой складской учёт, загрузка изображений в Storage, возвраты Stripe, промокоды, восстановление пароля, админка заказов, автоматические тесты и физическое удаление товаров, на которые могут ссылаться заказы.

### Решение по username и административному входу

Рекомендуемый вариант: Supabase Auth использует email/password, а уникальный `username` хранится в `profiles` и показывается в интерфейсе. Администратор — обычный Auth-пользователь с серверной ролью `admin`.

Пара `admin / 12345` не должна быть захардкожена в React, Git или базе в открытом виде. Supabase штатно принимает пароль вместе с email или телефоном, но не с username. Настоящий вход `username + password` потребует отдельной защищённой Edge Function, защиты от перебора и единого сообщения об ошибке; это дополнительные 6–10 часов и высокий риск для срока. До отдельного решения используем email/password плюс username профиля.

### Архитектура данных и интеграций

- `profiles`: `id -> auth.users.id`, уникальный `username`, имя, роль или связь с отдельной таблицей ролей.
- `orders`: пользователь, статус, итог, валюта, контакты доставки, Stripe Checkout Session ID, даты.
- `order_items`: заказ, product ID, снимок title/image/unit price, quantity и line total.
- `products`: существующие `discount_price`, `is_available` и `is_active` используются для скидки, отсутствия на складе и архивирования.
- Edge Function `create-checkout-session`: принимает только ID и количество, заново читает активные товары и рассчитывает цену на сервере.
- Edge Function `stripe-webhook`: проверяет `Stripe-Signature`, идемпотентно переводит заказ в оплаченный или неуспешный статус.
- RLS: покупатель читает только свои профиль и заказы; только admin может создавать, обновлять и архивировать товары; публичный каталог читает только активные товары.
